# 0181 — Listend ping is generated on demand, not read from the store

Claim `B-0181`: at listend `b87dcac9a3c9e0059d90e698e2ec40fb2769ec41`,
HTTP, TCP, and UDP ping all call `wav::twinkle()` at response time, hash those
bytes with `AudioItem::new`, and return the same fixed audio and content hash.
Ping does not look up a stored item, does not expose a CID, and does not depend
on the daemon's seed or library contents.

## Order of behavior

1. The native protocol server and UDP carrier handle `Request::Ping` by
   generating `twinkle()` bytes, recomputing their BLAKE3 hash, and returning
   `Response::Audio { content_hash, bytes, cid: None }`.
2. HTTP `GET /ping` generates the same bytes, computes the same hash, and sets
   `ETag: "<hash>"`, `Cache-Control: public, max-age=31536000, immutable`, and
   `Content-Disposition: inline; filename="<hash>.wav"`. It serves `audio/wav`
   and applies the carrier's range parser.
3. Because `twinkle()` has no RNG, all three carriers on any daemon produce
   the same bytes and hash. `publish_generated` also stores that same item in
   an empty library, but ping does not consult that stored copy.
4. `Hello` is the state-disclosing request: it returns daemon name, protocol
   version, and current item count. Ping itself carries no item count, peer
   identity, address, or IPFS CID.

## What is durable, rejected, and left behind

Durable: nothing is changed by ping. It is a deterministic computation, so
there is no format or storage rejection path distinct from the generator's
fixed output. A failed or empty store still answers ping with the same bytes.
The fixed ETag and immutable cache header follow from byte identity, not from
a claim that every daemon keeps the item persisted.

The response is a liveness answer that happens to be real WAV audio. It does
not prove that the daemon accepted, retained, or can fetch any other item.
No carrier, HTTP request, or target test was executed.
